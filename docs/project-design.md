# Narralume 项目设计与实施基线

> 实施基线：Phase 0 已完成；Phase 1-7 从 Phase 1 开始
> 首个验证内容：《北派盗墓笔记》  
> 产品边界：通用长篇故事视觉说书平台，不绑定具体小说或题材

## 1. 产品目标

Narralume 管理长篇文本、章节证据、全书分集改编、长期资产、TTS、字幕、图片和视频渲染，最终形成可持续生产、可人工审核、可局部重做和可恢复的本地工作流。

首个工程基线已验证从一段完整故事弧生成 3～5 分钟、9:16 的静图说书视频。当前产品闭环扩展为：用户导入长篇原文后配置总集数与单集时长，系统通过固定、持久、可恢复的自动流水线完成必要章节分析、书籍级故事圣经、全书分集计划以及全部忠实稿和包装稿生成，再由用户逐集审核、继续媒体生产，并在“审核与导出”阶段完成生产就绪复核、分片渲染、最终视频生成、MP4 下载和可选项目包创建。20 分钟只可作为某次用户配置，不能成为产品常量。《北派盗墓笔记》用于验证约 500 万字、近 1800 章的真实长篇输入，但所有领域名称保持通用。

## 2. 独立边界

- 独立 Git 仓库、依赖、数据库、数据目录、任务进程和导出目录；
- 不在 MuseDock 中增加模式、页面、路由或工作流；
- 不运行时依赖任何参考项目；
- 参考项目只作为设计和最小代码抽取来源；
- 大型原文、图片、音频和视频保存在文件系统，SQLite 只保存结构化数据、状态和相对路径。

## 3. 技术决策

| 项目     | 决定                                                               |
| -------- | ------------------------------------------------------------------ |
| 前端     | React + TypeScript + Vite + Tailwind CSS，通用控件优先 `shadcn/ui` |
| 后端     | Fastify + TypeScript                                               |
| 数据库   | SQLite，直接使用迁移和 SQL，首版不引入 ORM                         |
| 文件上传 | Phase 1 使用 Fastify 原始请求流导入 TXT；需要多文件表单时再引入 `@fastify/multipart` |
| 后台任务 | SQLite 持久化任务 + 单本地 Worker                                  |
| 视频     | 系统 `ffmpeg` / `ffprobe`                                          |
| 字幕     | SRT 保存、ASS 烧录                                                 |
| 时间轴   | 真实 TTS 时长驱动画面                                              |
| 图谱     | MVP 使用结构化章节事件，不引入图数据库                             |
| 桌面封装 | MVP 不做 Electron，确有安装需求时再加入                            |

Fastify 提供路由 Schema、统一错误边界、流式上传和插件生命周期，又不需要 NestJS 的依赖注入和装饰器体系。API 与 Worker 可以先运行在同一 Node 进程，但任务必须先写入 SQLite，不能依赖 HTTP 请求存活。

## 4. 参考项目分工

1. DramaClaw：小说摄入、章节预览、长篇知识组织、分集生产、任务状态和恢复；
2. Toonflow：章节按需取证、改编工作区、主资产/状态资产、候选图和显式关系；
3. LumenX：Series/Episode、系列共享资产、人物候选和变体；
4. LocalMiniDrama：SQLite、单项目包、TTS、SRT、FFmpeg 和生成历史；
5. MuseDock：模型调用、TTS 时间轴、音频检查、镜头数学和 FFmpeg 执行。

不整仓 fork 任何参考项目。抽取项按 `copy`、`port`、`reference-only` 分类，并记录在 `docs/source-provenance.md`。

## 5. MVP 流水线

```text
导入长篇 TXT
-> 编码识别、章节偏移和哈希
-> 配置改写范围、总集数与单集时长
-> 后台批量补齐结构化章节事件
-> 构建可追溯的书籍级故事圣经
-> 生成并校验全书分集计划
-> 原子冻结全部 Episode 与 episode_sources
-> 按分集顺序自动生成全部忠实稿和包装稿
-> 用户逐集审核与局部重做
-> 人工批准
-> TTS、真实时长和字幕
-> 主资产、状态资产和视觉段
-> 批量生图、候选选择和联系表
-> ffmpeg 分片渲染
-> 最终拼接与完整性复验
-> 下载 MP4；可选创建可恢复项目包
```

人工批准稿件是 TTS 和生图的硬闸门。

### 5.1 全本改写前端信息架构

正常用户路径统一为：

```text
导入小说
-> 全本改写设置
-> 全本生产进度
-> Episode 列表
-> 单集稿件审核
-> 单集媒体生产
-> 审核与导出
```

- “全本改写设置”配置连续改写范围、总集数和单集时长，局部区域只保留一个主操作“开始全本改写”；启动后禁止重复提交。
- “全本生产进度”读取持久 run 与 Job 的真实状态，分别显示章节事件、故事圣经、分集计划、忠实稿和包装稿的完成数量、当前对象及失败项；支持暂停、继续、取消和局部重试，不用无法由后端证实的百分比。
- “Episode 列表”是系列级主入口，每行显示“第 N 集 / 共 N 集”、标题、来源章节范围、忠实稿/包装稿状态和失败或待审核状态；已完成稿件的 Episode 可在全书其余稿件仍生成时提前进入审核。
- “单集稿件审核”“单集媒体生产”和“审核与导出”复用现有工作台、版本、批准、Job、最终视频与项目包核心，不复制第二套编辑器、渲染器或导出存储；上一集、下一集和 Episode 列表承担主导航，现有 `episodeIndex` URL 参数继续用于深链接与恢复。
- 章节事件页面退为高级检查和失败修复入口，不再要求用户逐章点击“自动分析本章”；Episode、稿件、音频和视觉阶段中重复的裸数字“分集序号”输入应移除，或仅保留为调试/恢复入口。
- 所有长任务使用稳定状态条和中文“正在进行、成功、失败、中断”反馈；状态不能只靠颜色，数量、时长和 Job ID 使用等宽数字，交互目标至少 44×44px，窄屏按单栏步骤流展示。

### 5.2 单集审核与导出

“审核与导出”不是新的媒体生产系统，而是既有 `render_chunks`、`final_video`、最终 manifest 和项目包能力的用户可见接线：

```text
选择 Episode
-> 核对稿件批准、时间轴、字幕、视觉覆盖、候选图批准和联系表生产就绪状态
-> 创建或恢复 render_chunks Job
-> 分片全部成功后创建或恢复 final_video Job
-> 回读并校验最终 manifest
-> 预览或下载当前有效 MP4
-> 可选在服务端受控目录创建可恢复项目包
```

- 一个区域只显示当前可执行的一个主操作：依次为“开始分片渲染”“生成最终视频”“下载 MP4”；“创建可恢复项目包”为最终视频成功后的次要操作。
- 页面显示真实 Job 状态、Job ID、时长、字节数和 SHA-256，支持取消、失败 Job 局部重试、刷新与后端重启恢复；不得以伪造百分比或旧文件冒充当前结果。
- MP4 下载必须由服务端根据数据库和 canonical manifest 受控读取，复核 Episode、时间轴、批准 revision、稿件版本、导出 hash、普通文件、受控路径、字节数和 SHA-256；不得接受客户端任意文件路径。
- 最终视频与可恢复项目包是两个输出：浏览器可下载 MP4；首版项目包由服务端在受控目录创建并返回路径和 manifest。现有项目包是目录，未定义归档格式前不伪装成单文件下载。
- 流水线不自动批准稿件、图片、音频或最终成片；任何上游失效都会禁用旧视频下载并明确提示需要重做的阶段。

## 6. 最小领域模型

- `books`：书名、作者、编码、原文件哈希和导入状态；
- `chapters`：稳定 ID、章节顺序、标题、字符偏移、字数和内容哈希；
- `chapter_events`：人物、地点、道具、因果、揭示、悬念和原文范围；
- `series_projects`：一个长期内容系列及默认风格和模型；
- `series_pipeline_runs`：系列级固定自动流水线的配置、阶段、暂停、失败和恢复身份；
- `series_pipeline_jobs`：只映射系列 run、阶段、对象与既有 Job，不复制 Job 状态和结果；
- `book_story_bibles`：由章节事件分层聚合、带来源和输入哈希的书籍级故事圣经；复用 identity 只含书籍、事件集合 hash 和合同版本，provider/model 仅作生成溯源；
- `episodes`：分集编号、阶段、目标时长、前情和下一集钩子；
- `episode_sources`：分集引用的章节和精确原文范围；
- `script_versions`：忠实稿、包装稿和批准稿；
- `assets`：人物、场景、道具及主资产/状态资产关系；
- `asset_aliases`：不同称呼归一到稳定资产；
- `asset_candidates`：生成或上传的候选图和当前审核状态；
- `visual_segments`：旁白范围、时间、画面、运动和选中图片；
- `visual_segment_assets`：视觉段引用的资产；
- `audio_segments`：TTS 文本、文件、真实时长和输入哈希；
- `subtitle_cues`：字幕时间和文本；
- `render_chunks`：1～3 分钟视频分片和输入哈希；
- `jobs`：持久化任务、租约、进度、错误和取消请求；
- `exports`：最终视频、字幕、清单和版本；项目包继续复用既有项目包 manifest/目录合同，不另建第二套 export/store。

状态和关系表是唯一业务真相，不再维护一份重复的大型工作区 JSON。

## 7. MVP 不做

- 受控 Agent、Decision Agent、Agent chat memory、多 Agent 对话和无限自动反思；
- 把 20 分钟、固定集数、固定章数或固定字数写成产品常量；
- AI 角色动画、口型同步和 AI 视频生成；
- 无限画布和通用节点系统；
- Hugging Face、Cognee、向量记忆和图数据库；
- HyperFrames 和 Chrome/Playwright 视频渲染；
- 多用户、云队列、权限和自动发布；
- 多套视觉模板和自动爆款评分。

## 8. 实施阶段

### Phase 0：独立骨架

**已完成。** React/TypeScript 前端、Fastify/TypeScript 后端、健康检查、测试和构建均已落地；基线提交为 `e75b1c3`。

### Phase 1：书库与章节

真实大 TXT 流式导入，支持 UTF-8、GBK/CP936、GB18030、章节偏移、哈希和重复编号。

验收：使用真实长篇 TXT 经 HTTP 流式落盘，不把整本书保存在数据库或请求内存中；正确识别上述编码，生成稳定书籍/章节 ID、原始字节偏移、字符数和 SHA-256；重复导入幂等，重复章节编号不覆盖；重启后可从 SQLite 查询书库、章节列表和原文切片。

### Phase 2：任务与章节事件

SQLite Worker、租约、中断恢复、重试、取消请求和结构化章节事件。

验收：任务先持久化再执行；进程中断后租约可回收并从 checkpoint 恢复；重试和取消可观察且不会生成双份结果；至少一组真实章节生成并保存带精确原文范围的结构化事件。

### Phase 3：分集与改编

故事弧、原文证据、忠实稿、包装稿、版本和人工审稿闸门；全本固定自动流水线是基于该既有 Phase 3 能力新增的产品闭环。

既有 Phase 3 验收：真实分集的故事弧、来源证据、忠实稿/包装稿不可变版本、人工批准/撤回及生产硬门已完成，并以 Delivery Ledger 的 P3-01～P3-04 历史证据为准。新增的全本设置、批量章节分析、故事圣经、分层全书规划、原子冻结和批量稿件不追溯改写 Phase 3 完成状态，由 `REQ-AUTO-01～04` / `AUTO-01～04` 单独承载和验收；未完成这些 AUTO Requirement 时不得宣称“固定自动全本改写流水线完成”。

### Phase 4：TTS 与字幕

先完成黑底或占位图的有声字幕视频，验证按 Episode 配置时长生成的真实旁白时间轴。

验收：真实 TTS 音频经 `ffprobe` 取得时长，生成不越界的 SRT/ASS 时间轴，并产出一条按 Episode 配置目标时长生成的有声字幕占位视频；相同输入可复用，音频变化会使下游 checkpoint 失效；3～5 分钟只保留为已验证工程样例，不作为产品常量。

### Phase 5：资产与图片

主资产、状态资产、别名、候选图、视觉段、显式绑定和图片联系表。

验收：真实样片所需人物、场景、道具可建立主/状态资产和别名；每个视觉段只通过显式关系引用已登记候选图；候选选择、来源和审核状态可追溯；可导出图片联系表供人工审核。

### Phase 6：FFmpeg 成片

唯一 9:16 模板、静图微动、淡化、ASS 字幕、分片恢复和 concat 导出。

验收：系统 `ffmpeg` 以唯一 9:16 模板完成静图微动、淡化和 ASS 烧录；按 1～3 分钟分片渲染，失败后只重做失效分片；`concat` 输出经 `ffprobe` 验证分辨率、音视频流和时长，且无缺失输入仍被标记成功的情况。

### Phase 7：真实样片与项目包

完成第一条真实样片、“审核与导出”前端闭环、单项目备份恢复，并记录成本、耗时、失败率和人工耗时。

验收：从真实长篇原文完成一条按 Episode 配置目标时长生成的 9:16 可播放样片，不把 3～5 分钟或 20 分钟硬编码为产品策略；用户可从前端审核真实生产就绪条件、创建或恢复分片与最终视频 Job，并只下载通过 manifest、路径、字节数和 SHA-256 复核的当前 MP4；可选在服务端受控目录创建包含数据库、原文、批准稿、音频、字幕、图片、分片、最终视频、清单与校验哈希的可恢复项目包；在空数据目录恢复后能够查询证据并重新导出；记录成本、总耗时、失败率、重试次数和人工耗时；全量验证与适用 Review 无未解决阻断项。

Phase 1-7 的当前阶段、动态进度、证据和恢复入口只记录在 [`loop/phase-1-7-delivery-ledger.md`](loop/phase-1-7-delivery-ledger.md)。

## 9. 升级条件

- SQLite 结构化事件确实无法满足跨数百章查询时，才评估图谱或向量索引；
- 单 Worker 成为真实瓶颈时，才增加并发 Worker；
- 两个项目反复维护同一模块时，才建立独立共享包；
- 固定模板无法表达已验证的高价值画面时，才增加浏览器渲染或第二模板；
- 本地 Web 启动成为实际障碍时，才加入 Electron；
- 静图内容的真实发布数据明显不足时，才选择性加入图生视频。
