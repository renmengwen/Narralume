## 1. 最终目标

最终目标不是继续给 MuseDock 增加一个普通创作模式，而是创建一个独立的新项目，专门生产“长篇小说说书视频”。

新项目应：

- 以《北派盗墓笔记》作为首个真实、长期改编对象；
- 参考抖音博主“超卜说书”的成熟视频形态；
- 复用 MuseDock 已验证的核心能力，而不是复制整个 MuseDock；
- 围绕长篇小说导入、章节索引、分集改编、人物一致性、批量生图、长 TTS、字幕和长视频恢复能力做专项优化；
- 第一阶段只做“AI 生图 + 配音 + 字幕 + 静图微动 + 淡化换图”的可靠成片，不投入角色动画和复杂 HTML 动效；
- 最终形成可连续生产、可恢复、可人工审稿、可追溯原文的独立产品。

## 3. 参考视频的核心产品形态

参考视频不是依赖复杂动画取胜，而是依赖以下组合：

1. 选择自带冲突、危险或谜团的小说片段；
2. 在原故事前增加 2～3 个明确问题；
3. 承诺“用 AI 复刻原著场景”；
4. 用高密度旁白持续推动剧情；
5. 为关键人物、地点、怪物、器物和反转生成 AI 场景图；
6. 使用白色一到两行字幕；
7. 对静图施加非常轻的推近、平移或呼吸效果；
8. 使用淡化换图，不依赖复杂转场；
9. 在新危险、人物异常或谜底揭晓前结束，驱动下一集追更。

可概括为：

```text
小说原文
  -> 分集与口播整理
  -> 开头问题钩子
  -> 场景图规划与生图
  -> TTS
  -> 同步字幕
  -> 静图微动与淡化换图
  -> 分段渲染
  -> ffmpeg 拼接导出
```

## 4. 旁白与字幕分析结论

### 4.1 旁白的主要优点

- 信息密度高，几乎没有长时间空镜；
- 每隔一小段就出现新地点、新物体、新危险或新信息；
- 原文包含大量可以直接转成视觉提示词的场景细节；
- 适量加入主播口吻和粉丝梗，降低纯小说朗读感；
- 对熟悉原著人物和设定的核心用户非常友好；
- 连续更新时，“书接上回”形成稳定的追更预期。

### 4.2 旁白的主要问题

- 更接近剧情复述，不一定是真正的深度“精讲”；
- “为什么”“到底是什么”“我将用 AI 复刻”等句式重复较多；
- 约 330～370 字/分钟的持续语速偏快，20 分钟内容可能造成疲劳；
- 对不熟悉人物关系的新观众缺少一句话前情复位；
- ASR 中存在专有名词错误，说明新项目必须维护人物、地点、器物和生僻字词典；
- 配音音色、重音、停连和情绪仍需通过实际听音单独评估，不能只依靠 ASR 判断。

### 4.3 字幕的优点

- 白色一到两行，阅读成本低；
- 位于中下部，没有压到平台底部操作区；
- 不使用复杂花字和频繁动画，适合长视频批量生产；
- 与暗黑场景风格基本协调；
- 简单模板降低长视频渲染和布局失败概率。

### 4.4 字幕的不足

- 部分字幕叠在手电筒或其他亮部上，反差下降；
- 缺少关键词层级和专有名词纠错；
- 个别字幕偏长；
- 新项目应优先保证断句、描边、阴影、两行上限和安全区，不必第一版加入卡拉 OK 高亮。

## 5. 开头与结尾钩子结论

### 5.1 开头

31 条完整 ASR 中，约 23 条在前 180 字内出现明确问句或悬念；近期 6 条全部使用明确问题钩子和“书接上回”。

近期成熟结构为：

```text
异常现象是什么？
人物为什么会这样？
接下来会遇到什么？
我将用 AI 复刻他们遇到的场景。
好了，书接上回……
```

高互动样本前 16 秒约出现 4 个不同场景，能够快速兑现开头问题；同期低互动样本前 16 秒基本停留在同一张图，并直接从上一集正文进入，对新观众不友好。

新项目的默认开头节奏建议：

- 0～3 秒：最异常、最危险或最反常的一句话；
- 3～8 秒：提出一个具体问题；
- 8～12 秒：给出视觉化承诺；
- 12～15 秒：一句前情复位；
- 15 秒后进入正文；
- 开头 15 秒使用 3～4 张图，换图速度明显快于正文。

开头文案不应永远使用同一种“到底是什么”，至少轮换：

- 异常型；
- 禁忌型；
- 代价型；
- 冲突型；
- 身份反转型；
- 结果前置型。

### 5.2 结尾

有效结尾通常停在：

- 人物突然说出反常信息；
- 新怪物或新地点即将出现；
- 身份即将揭晓；
- 原有判断被推翻；
- 主角即将进入不可逆的危险。

31 条完整 ASR 中，只有约 4 条在结尾包含明显的点赞、关注或继续更新 CTA。最高互动的近期样本反而没有冗长 CTA，说明故事悬念比反复求赞更重要。

新项目结尾应优先生成“下一集的具体问题”，CTA 最多一句。

这些数据支持以下方向判断：

- 明确问题钩子值得保留；
- 连载承接和原著粉丝价值很强；
- 分享和收藏很高，说明用户把它当成可持续消费的长内容，而不只是看一眼的 AI 图片；
- 开头快速换图可能比正文持续高频换图更重要。

不能直接得出的结论：

- 钩子带来了多少精确增长；
- 某种换图频率必然提高完播；
- 某种字幕样式优于另一种字幕样式；
- 视频的播放完成率和点赞率。

原因是抓取元数据中的 `play_count` 为 0，且发布时间、账号权重和选题热度没有控制。新项目必须通过真实发布数据验证，而不是把样本相关性当成因果关系。

## 9. 不应直接复用的现有假设

MuseDock 当前一键创作主要面向 45～75 秒短视频，新项目需要主动移除或改写以下限制：

- 当前创作入口不能上传 TXT；
- 服务端 JSON 请求上限约 2 MB，不能直接粘贴约 500 万字小说；
- 通用创意规格中的来源正文会被截断；
- 通用改写上下文约 8000 字，不能一次消费整本小说；
- 当前 UI 目标时长上限约 600 秒；
- 当前单视频 AI 生图数量上限约 20 张；
- 当前提示词偏向 45～75 秒、约 60 秒视频；
- 当前复杂 Frame HTML、信息卡和布局 QA 对说书静图视频不是核心价值；
- 当前逐场景文字生图不足以保证同一人物跨几十张图的一致性。

## 12. 小说导入与索引要求

新项目必须从第一版支持：

- UTF-8；
- GBK/CP936；
- GB18030；
- 章节标题识别；

- 超大 TXT 本地读取，不通过单个 JSON 请求上传全文；
- 只把当前分集需要的有限原文发送给模型。

《北派盗墓笔记》章节号会在不同卷或内容段中重复，新项目不能只用“第 101 章”作为唯一键。推荐内部键至少包含：

```text

```

## 13. 分集策略

不能机械执行“每章一集”或“每三章一集”。

建议先按目标字数寻找相邻章节，再按故事弧调整边界：

- 3～5 分钟试片：约 1000～1800 字；
- 8～10 分钟：约 2600～3400 字；
- 15～20 分钟：约 5000～7000 字；
- 20～25 分钟：约 6800～8500 字。

候选结束点：

- 新人物即将出现；
- 行动目标发生变化；
- 主角意识到被骗；
- 一个物件被识别；
- 危险刚被看见但尚未解决；
- 人物做出不可逆选择；
- 原有判断被推翻。

每个分集工程必须保存：

- 原文起止章节；
- 原文起止字符位置；
- 使用和省略的原文片段；
- 改编稿；
- 开头钩子；
- 前情复位；
- 结尾悬念；
- 下一集承接问题；
- 已知人物状态；
- 已揭示和未揭示的信息。

## 14. 改编策略

第一版采用三层处理，不让模型自由重写整段故事。

### 14.1 忠实整理层

只允许：

- 书面语转成自然口播；
- 明确对话归属；
- 修复代词歧义；
- 合并不影响情节的重复动作；
- 删除排版噪音；
- 统一专有名词；
- 控制旁白长度；
- 保持原始事件顺序和因果。

### 14.2 包装层

允许新增：

- 开头悬念；
- 前情复位；
- 必要背景解释；
- 章节过渡；
- 结尾追更问题；
- 少量、稳定的主播口吻。

### 14.3 视觉规划层

只负责提取和规划：

- 人物；
- 地点；
- 时间；
- 动作；
- 重要器物；
- 光线；
- 情绪；
- 镜头景别；
- 人物一致性字段；
- 生图提示词。

## 15. 《北派盗墓笔记》的专项文案方向

《北派盗墓笔记》不应完全套用参考博主的南派问题模板。

优先使用：

- “我亲历过什么”；
- “一个选择付出了什么代价”；
- “这一行真正的规矩是什么”；
- “看似普通的人为什么危险”；
- “这件古董为什么不能碰”；
- “一次交易如何变成骗局”；
- “当时的我还不知道，后来会发生什么”；
- “为什么有人开出高价，我却不敢答应”。

第一人称是这部小说的重要资产。除非明确选择第三人称说书模式，否则改编稿应尽量保留“我”的现场感，不应把所有段落改成旁观者百科解说。

## 16. 人物与视觉一致性

每个主要人物建立固定设定卡：

- 姓名与常用称呼；
- 年龄阶段；
- 性别；
- 脸型；
- 发型；
- 体型；
- 服装；
- 常用道具；
- 主要色彩；
- 性格和表情范围；
- 禁止变化项；
- 可选参考图。

每个分集还要保存阶段状态：

- 当前年龄；
- 当前地点；
- 当前服装；
- 是否受伤；
- 携带物品；
- 与其他人物的相对位置。

第一版先使用固定文本前缀和已生成图片审核；只有当前生图供应商真实支持参考图时，再加入参考图一致性，不提前设计一套供应商无能力消费的抽象接口。

## 17. 第一版视频模板

### 17.1 渲染技术选型

第一版确定直接使用 `ffmpeg` 实现固定模板，不使用 HyperFrames，不依赖 Chrome/Playwright，也不为每个镜头生成 HTML。

首版所需的全屏图片、9:16 `cover` 裁切、轻微推拉和平移、淡化换图、ASS 字幕烧录、暗角、颗粒、BGM 混音和分片拼接均可由 `ffmpeg` 完成。推荐以 1～3 分钟为一个渲染分片，在分片内一次完成图片时间轴、镜头运动、转场、字幕和音频合成，避免先为每张图片生成独立视频再反复转码。

每个分片应使用一致的分辨率、帧率、像素格式、视频编码和音频采样率，使最终成片可以优先通过 concat 直接拼接。修改旁白、字幕或图片时，只重新生成受影响的分片。

只有真实发布数据或明确编辑需求证明固定模板不足时，才考虑引入 HyperFrames，例如需要复杂信息卡、多元素排版、可视化标注、GSAP 动画或浏览器内所见即所得编辑。HyperFrames 不作为第一版的预留依赖。

### 17.2 模板规格

只做一套 9:16 模板：

- 全屏 AI 图片；
- `cover` 裁切；
- 轻暗角；
- 可选轻颗粒；
- 白色双行字幕；
- 轻描边和阴影；
- 字幕底部安全区；
- 每张图缓慢 `scale(1.03 -> 1.08)`；
- X/Y 平移控制在画面宽高约 1%～2%；
- 0.4～0.8 秒淡化换图；
- 可选 BGM；
- 可选顶部账号名或系列名；
- 不生成角色动作或口型。

建议画面节奏：

- 开头 15 秒：每 2～5 秒一张图；
- 普通正文：每 12～25 秒一张图；
- 关键反转：每 4～8 秒一张图；
- 情绪或解释段：允许一张图保持更久；
- 同一张图可通过全景、轻推近、局部裁切复用，降低成本和人物漂移。

## 18. 长视频渲染与恢复

不要一次性渲染 20 分钟成片。

推荐：

- TTS 按段生成并立即落盘；
- 生图逐张落盘；
- 每张图、每段音频和每段字幕有独立状态；
- 每 1～3 分钟生成一个视频分片；
- 失败时从当前分片恢复；
- 不启动 Chrome，不执行网页逐帧截图；
- 修改图片、字幕或旁白后，只重新渲染受影响的分片；
- 最后使用 `ffmpeg` 无损或最小重编码拼接；
- 保存实际音频时长，画面时长以真实 TTS 为准；
- 导出前检查黑帧、缺图、缺字幕、字幕溢出、音频静音和总时长。

## 19. MVP 建议

### MVP 目标

从《北派盗墓笔记》选择一个完整小故事弧，产出一条 3～5 分钟、可人工审核、可重复生成的 9:16 样片。

### MVP 必须包含

- 导入《北派盗墓笔记》GBK TXT；
- 解析并浏览章节；
- 选择一段原文；
- 生成忠实口播整理稿；
- 生成开头钩子、前情复位和结尾悬念；
- 人工确认文案后再继续消费生图和 TTS；
- 生成约 8～15 张图；
- 生成 TTS；
- 生成同步字幕；
- 使用固定静图微动模板；
- 分段渲染并导出 MP4；
- 保存工程并支持失败恢复；
- 可以修改旁白、字幕或某张图片后重新导出。

### MVP 不追求

- 一键处理整本小说；
- 直接生成 20 分钟成片；
- 多套视觉风格；
- 完全自动的人物一致性；
- 自动发布；
- 自动保证爆款。

## 22. Toonflow 参考项目深入分析

### 22.1 审查范围与版本

参考仓库：[`HBAI-Ltd/Toonflow-app`](https://github.com/HBAI-Ltd/Toonflow-app)

本次结论不是只根据 README 和演示截图得出，而是核对了当前公开源码中的数据库结构、小说路由、章节事件提取、ScriptAgent、ProductionAgent、资产与图片表、分镜与视频轨道、任务记录、数据库备份以及官方截图。

审查快照：

- 提交：`bc61ec7a1b5df31293b286981a5f4ad4635464ee`；
- 提交时间：2026-07-09；
- 应用版本：`1.1.8`；
- 后端：Node.js、TypeScript、Express、Socket.IO；
- 本地数据：SQLite/Knex；
- 桌面端：Electron；
- AI 调用：Vercel AI SDK 和可编程供应商适配；
- 前端源码未完整公开，仓库主要提供 `data/web` 下的编译产物，因此 UI 可以作为产品设计参考，但不适合直接提取组件复用。

许可证需要特别注意：仓库声明 Apache-2.0，同时在 `LICENSE` 和 README 中附加了商业分发、标识保留和第三方使用数量限制。当前使用边界已经明确为用户自己或内部团队使用，不向独立第三方分发产品，也不对外提供 Toonflow 衍生服务；这属于其补充协议列明的“二次开发供自己团队内部使用”永久免费场景。因此，新项目可以在满足 Apache-2.0 和补充协议的前提下选择性复用 Toonflow 源码，不必默认只做思想借鉴。

复用时应保留原有版权声明，在项目中保存 Toonflow 的 `LICENSE`、`NOTICES.txt` 和来源提交，标记做过实质修改的文件，并记录抽取模块和改动。若直接继续使用 Toonflow 控制台或应用，不删除或修改其现有标识和版权信息。以后如果使用边界变为向两个及以上独立第三方分发、销售、授权或提供服务，再重新核对商业授权要求。

### 22.2 Toonflow 的真实产品结构

Toonflow 的主流程可以概括为：

```text
项目
-> 导入并分页管理小说章节
-> 为每章生成事件摘要
-> ScriptAgent 生成故事骨架、改编策略和分集剧本
-> 从剧本提取角色、场景和道具资产
-> 为主资产生成标准图
-> 基于主资产生成服装、状态等衍生资产
-> ProductionAgent 生成导演规划、分镜表和分镜面板
-> 将资产显式绑定到分镜
-> 按 Track 组织图片、音频和视频引用
-> 生成提示词、分镜图或视频
```

其核心数据关系不是一个大 JSON，而是由多个实体组成：

| Toonflow 实体 | 实际职责 | 对新项目的价值 |
|---|---|---|
| `o_project` | 项目名、简介、题材、画风、画幅和默认模型 | 中高 |
| `o_novel` | 每章一行，保存章节序号、卷、标题、正文、事件摘要和状态 | 高 |
| `o_script` | 分集剧本 | 高 |
| `o_agentWorkData` | 故事骨架、改编策略、生产工作区等 JSON | 中 |
| `o_assets` | 角色、场景、道具、音频和素材；支持父子资产 | 高 |
| `o_image` | 一项资产的多个生成结果及状态 | 高 |
| `o_scriptAssets` | 分集剧本与资产的多对多关系 | 高 |
| `o_storyboard` | 分镜说明、提示词、时长、图片和轨道 | 中高 |
| `o_assets2Storyboard` | 资产与分镜的多对多关系 | 高 |
| `o_videoTrack` / `o_video` | 生产轨道和候选视频结果 | 第一版低 |
| `o_tasks` | AI 任务分类、状态和错误原因 | 中高，但实现不能照搬 |

这个拆分方式比“把整本小说、剧本、人物设定和图片都塞进一个项目 JSON”更适合长期连载。新项目应借鉴实体边界，但使用符合说书视频的字段，不复制 Toonflow 的表名和短剧视频生成假设。

### 22.3 小说导入、章节管理与事件分析

#### 值得借鉴

Toonflow 将小说拆成逐章记录，而不是每次把整本书传给模型。每章都能独立分页、搜索、编辑、删除、重新生成事件，并保存：

- 章节顺序；
- 卷名；
- 章节标题；
- 原文；
- 事件摘要；
- 事件生成状态；
- 错误原因。

事件提取按章运行，默认最多 5 个并发任务。ScriptAgent 不会默认把全书正文塞入上下文，而是先通过工具查询指定章节的事件摘要，需要原文时再读取单章正文。这种“先粗粒度索引，再按需取原文”的上下文控制非常适合约 500 万字、1791 章的《北派盗墓笔记》。

新项目应采用相同原则，但事件摘要必须结构化并服务于说书分集，而不是只保存自由文本。建议至少包含：

- 主要人物；
- 地点和时间；
- 发生的动作与结果；
- 因果关系；
- 新信息和已揭示信息；
- 冲突、危险、骗局、代价或人物选择；
- 可视化价值；
- 与主线的关系；
- 可作为开头的问题；
- 可作为结尾的悬念；
- 原文章节和字符范围。

#### 不能直接照搬

Toonflow 后端的新增小说接口接收的是前端已经切分好的章节数组；公开源码中没有可独立审查和复用的完整 TXT 编码识别与章节解析实现。它没有覆盖本项目已经明确要求的 GBK/CP936、GB18030、约 500 万字文件、源字符偏移、原文片段哈希、跨卷重复章节号和稳定内部键。

此外，README 将其描述为“章节事件图谱”，但当前公开代码中的主路径主要把一个事件结果字符串写回 `o_novel.event`。仓库虽然定义了 `o_event` 和 `o_eventChapter`，却没有发现事件生成流程向这两张表写入事件节点和章节关系的实现。因此，当前更准确的说法是“章节事件摘要索引”，不是已经成熟的跨章事件图谱。

新项目第一版也不需要真正的图数据库。使用 SQLite 中的结构化章节事件表，加上人物、地点、物件和前后因果字段即可；只有跨数百章关系查询确实出现性能或表达瓶颈时，再考虑图结构。

### 22.4 小说分析与改写工作区

Toonflow 把编剧工作拆成三种明确产物：

1. 故事骨架；
2. 改编策略；
3. 分集剧本。

同时使用决策层、执行层和监督层 Agent：决策层判断下一步，执行层分别生成骨架、策略和剧本，监督层独立检查；提示词以 Markdown Skill 文件保存，模型可以调用工具读取章节事件、指定章节原文、已有剧本和当前工作区。

这里最值得复用的是“产物分层”和“按需取证”，不是三层 Agent 的数量。北派说书项目应将工作区调整为：

```text
原文范围与证据
-> 故事弧和分集边界
-> 忠实整理稿
-> 包装层：开头钩子、前情复位、过渡、结尾悬念
-> 视觉段规划
-> 人工审稿确认
```

每层都应保存独立版本和上游引用。修改包装层不应覆盖忠实整理稿；修改口播稿后，应能识别哪些字幕、TTS 和视觉段需要失效重做。

第一版不建议照搬 Toonflow 的通用决策 Agent、多个执行子 Agent、监督 Agent、向量记忆和在线 Skill 管理。对一个固定题材、固定流程的 MVP，确定性的阶段按钮、结构化输出、一次独立审稿和明确的“继续生成”闸门更便宜、更容易恢复，也更容易定位模型错误。Markdown 提示词文件、版本号和可编辑能力值得保留，但不必先建设完整 Skill 市场或语义检索系统。

### 22.5 项目与分集管理

Toonflow 的项目首页以卡片呈现项目，项目内再固定进入原著、编剧、剧本、资产、生产和素材等工作区；项目级保存题材、简介、画风、画幅和默认模型，分集级保存剧本、资产关系、分镜和生产数据。这个“项目是系列，剧本是分集”的层级很适合连续生产。

新项目建议采用：

```text
书库 Book
└─ 系列项目 Series Project
   ├─ 人物与世界设定
   ├─ 全局专有名词库
   ├─ 视觉风格与默认模型
   └─ 分集 Episode
      ├─ 原文证据范围
      ├─ 改编工作区
      ├─ 视觉段与资产引用
      ├─ TTS 和字幕
      ├─ 渲染分片
      └─ 导出版本
```

项目卡片不应只显示标题和简介，还应显示对长任务真正有用的信息：当前分集、最后更新时间、进行到的阶段、失败任务数、待人工审核项和最近导出结果。删除项目必须经过二次确认，并区分“移入回收站”和“永久删除”，不能直接照搬 Toonflow 的多表和目录立即删除。

Toonflow 提供 SQLite 数据的整体 JSON 导入导出，说明本地项目备份是重要能力。但它的导入逻辑会删除并重建全部表，更像整库恢复。新项目首版应优先支持单项目可搬运包，并在导入前校验版本、清单和文件哈希，避免为导入一个项目覆盖其他项目。

### 22.6 人物一致性与资产系统

这是 Toonflow 最值得借鉴的部分。

#### 主资产与衍生资产

Toonflow 将角色、场景和道具作为主资产，为角色生成标准四视图；同一人物的不同服装或阶段状态作为子资产，通过 `assetsId` 指向父资产。生成衍生资产时，系统会读取父资产描述，并在供应商支持时把父资产图片作为参考图输入。这比为每个镜头重复拼一段人物提示词更可靠。

北派项目应采用同样的两层概念：

- 主资产：项云峰、把头、核心地点、重要古董等稳定身份；
- 状态资产：某年龄阶段、某次行动的服装、受伤状态、携带物品、表情和场景光线。

但状态资产不能无限复制。优先只为会跨多个视觉段重复出现的状态建立资产；只出现一次的轻微变化可以留在视觉段提示词中。

#### 候选图与当前选中图

Toonflow 的 `o_image` 会保存一项资产的多次生成结果，`o_assets.imageId` 指向当前选中的图片。这一设计值得直接借鉴为概念：生成失败不会覆盖旧图，用户可以查看历史候选并切换当前版本。

新项目还应补充 Toonflow 当前结构中不足的字段：

- 资产稳定 ID，不能用名称作为唯一身份；
- 别名和原文称呼；
- 结构化人物设定字段；
- 当前故事阶段；
- 禁止变化项；
- 参考图来源和授权信息；
- 使用的模型、提示词、种子或供应商任务 ID；
- 生成时间和审核状态；
- 失败原因；
- 当前选中版本；
- 被哪些分集和视觉段引用。

#### 资产关系

Toonflow 使用 `o_scriptAssets` 记录剧本使用哪些资产，使用 `o_assets2Storyboard` 记录每个分镜具体使用哪些资产。它在提取新剧本资产时，会把已有资产名称提供给模型，要求区分“新资产”和“已有资产引用”，从而减少重复创建。

这个方向正确，但不能只依赖名称匹配。北派项目应使用稳定资产 ID，加上别名表和人工合并入口；“我”“云峰”“项云峰”必须能够归一到同一人物。资产提取结果应先进入待确认区，人工确认新增、复用或合并后，再进入批量生图。

### 22.7 视觉段、分镜和生成资产绑定

Toonflow 把分镜保存为独立记录，包含说明、提示词、时长、轨道、生成状态、图片和关联资产 ID；多个分镜再按 Track 聚合，并为图像或视频模型组织参考图片、音频和候选生成结果。官方工作台截图中，资产卡、分镜表、分镜面板和生成结果可以同时在画布中查看，这对追踪上下游关系很直观。

北派说书第一版不需要完整的无限画布、视频生成轨道或复杂分镜表。应把分镜简化为“视觉段”：

- 对应哪段旁白和字幕；
- 开始和结束时间；
- 使用哪个主资产或状态资产；
- 使用哪张当前图片；
- 景别、构图、光线和情绪；
- 镜头运动参数；
- 淡化时长；
- 生成、审核和渲染状态。

仍应保留 Toonflow 的显式绑定思想：一张画面引用了哪些人物、场景和道具必须可查询。这样更换项云峰的标准形象时，系统才能列出受影响的视觉段，而不是盲目重做整集。

Toonflow 的分镜预览会用 Sharp 将多张图合成带编号的联系表。这个小功能成本低、价值高，建议新项目在 MVP 中加入“本集图片联系表”：一次查看 8～15 张图的角色漂移、色调跳变、重复构图和缺图，比逐张打开更适合人工审核。

### 22.8 任务状态、批量生成与恢复

Toonflow 为章节事件、剧本资产提取、图片、分镜和视频分别保存“生成中、已完成、生成失败”等状态，并支持批量选择、并发数和错误原因。这种“状态靠近产物”的方式值得借鉴。

但当前公开实现不等于可靠的长任务系统：

- 多个批量任务在 HTTP 返回后继续以内存 Promise 运行；
- 服务进程重启后不会自动恢复这些 Promise；
- 部分“取消”接口只是把数据库状态改成失败，没有真正中断供应商请求；
- `o_tasks` 主要用于记录和查询，不是持久化任务队列；
- 工作区 JSON 与分镜、资产等关系表并存，存在双写和状态不一致风险；
- “生成成功”“已完成”等状态词在不同路径不完全统一。

北派项目必须采用更严格的任务模型：

```text
pending -> running -> succeeded
                   -> failed
                   -> cancelled
                   -> interrupted
```

每个任务至少保存输入哈希、产物路径、上游版本、尝试次数、开始与结束时间、错误分类和可重试标志。重启时把遗留的 `running` 标记为 `interrupted`，由用户或恢复器重新入队。取消必须尽可能触发 `AbortController` 或供应商取消接口；如果供应商不支持取消，应显示“已停止等待结果，供应商任务可能仍在计费”，不能伪装成真正取消。

状态的唯一事实来源应是规范化产物表和任务表。前端画布位置等纯 UI 状态可以保存 JSON，但不能再复制一份资产、分镜和生成状态作为业务真相。

### 22.9 UI 和操作流程可借鉴点

根据官方截图，值得借鉴的交互包括：

- 项目卡片入口清晰，项目内主要阶段保持固定导航；
- 编剧对话与故事骨架、改编策略、剧本工作区并排，AI 过程和最终产物分离；
- 资产以角色、场景、道具分类，卡片同时显示描述、模型、分辨率和状态；
- 批量选择区明确提供“提示词为空、未生成、已生成、错误项”等快捷筛选；
- 原始资产和衍生资产以父子关系展示；
- 每个分镜可查看引用素材、提示词、历史生成结果和当前选中版本；
- 长流程右侧持续显示阶段进度和 Agent 的当前结论。

北派项目不应直接复制它的信息密度和无限画布。首版更适合固定步骤页，并在每一步提供：

- 本步输入；
- AI 输出；
- 来源证据；
- 待人工确认项；
- 失败项筛选；
- 批量重试；
- 继续下一步按钮；
- 明确的 loading、成功、失败和中断状态。

无限画布只有在用户确实需要自由重排大量分镜、分支版本和引用关系时再加入。对于 3～5 分钟、8～15 张图片的 MVP，表格、卡片和时间轴更直接。

### 22.10 其他值得借鉴的设计

#### 提示词与题材规则文件化

Toonflow 将 Agent 指令、题材规则、画风规则和模型专用视频提示词放在 Markdown 文件中。这有利于版本管理、人工修改和针对不同模型调整。新项目应采用文件化提示词，但第一版只需要北派说书、人物资产、场景资产、视觉段规划和忠实度检查几组固定模板，并为每次生成记录模板版本。

#### 供应商能力映射

Toonflow 会区分文本、图像和视频模型，并根据模型能力组织参考图、首尾帧、音频或多参数输入。新项目第一版虽然不生成 AI 视频，也应记录图像供应商是否支持参考图、最多参考图数量、比例、分辨率和任务查询方式，避免上层流程假设所有供应商能力相同。

#### 图片生成历史和局部编辑

Toonflow 允许同一资产保留多个图片结果，还提供一个图片节点工作流，将上传图和参考图连接到新一轮生成。这说明“历史候选 + 参考图重做”比覆盖式重新生成更适合资产生产。北派项目首版只实现候选历史、选中版本、上传替换和参考图重做，不建设通用节点编辑器。

#### 本地优先与可搬运

SQLite、项目目录和本地资源服务符合新项目的本地优先方向。需要改进的是备份粒度、原子写入、哈希清单和迁移版本，而不是改成云端优先架构。

### 22.11 明确的复用分级

| Toonflow 设计 | 结论 | 新项目做法 |
|---|---|---|
| 每章独立存储和分页 | 采用 | 增加编码、偏移、哈希和稳定章节键 |
| 章节事件摘要 | 采用并增强 | 使用结构化事件，不宣称首版是图谱 |
| 按需读取事件和原文 | 采用 | 模型只读取当前故事弧所需范围 |
| 故事骨架、策略、剧本分层 | 采用并改造 | 改成故事弧、忠实稿、包装层、视觉段 |
| 三层 Agent | 暂不采用 | 固定阶段 + 一次独立审稿足够完成 MVP |
| Markdown Skill | 简化采用 | 少量版本化提示词文件，不建 Skill 市场 |
| 项目/分集层级 | 采用 | 增加阶段、失败项、待审核和导出状态 |
| 主资产/衍生资产 | 采用 | 主人物 + 阶段状态资产 |
| 资产候选图和当前图 | 采用 | 保留历史、审核状态和生成来源 |
| 剧本/分镜/资产多对多关系 | 采用 | 使用稳定 ID，不只靠名称去重 |
| 图片联系表 | 采用 | 用于整集一致性人工审核 |
| 无限画布 | MVP 不采用 | 固定步骤、表格、卡片和时间轴 |
| 视频生成轨道 | 第一版不采用 | 继续使用静图微动 + `ffmpeg` |
| 向量 Agent 记忆 | 第一版不采用 | 连载事实写入结构化项目数据 |
| 后台 Promise 批任务 | 不采用 | 使用可恢复的持久化任务与检查点 |
| 仅修改状态的取消 | 不采用 | 真正中断或明确告知无法取消计费 |
| 整库覆盖式导入 | 不采用 | 单项目包、版本校验、哈希清单 |
| 可编程供应商 TypeScript | 第一版不采用 | 复用 MuseDock 已验证的供应商调用边界 |
| Toonflow 源码选择性复用 | 可以采用 | 当前为内部自用；保留许可证、NOTICE、来源提交和修改记录 |
| 整仓 fork Toonflow | 不推荐 | 产品边界过宽，优先抽取少量稳定模块或独立实现缺失部分 |

### 22.12 对 MVP 范围的直接调整

参考 Toonflow 后，北派项目的 MVP 应增加以下已经被真实产品证明有价值、且成本可控的能力：

- 章节级结构化事件摘要和失败重试；
- 分集工作区明确区分原文证据、忠实整理稿、包装层和视觉段；
- 角色、场景、道具资产库；
- 主资产与少量阶段状态资产；
- 每项资产的候选图历史、当前选中图和审核状态；
- 分集与资产、视觉段与资产的显式关系；
- 批量生图的未生成、生成中、失败、已完成筛选；
- 8～15 张本集图片联系表；
- 项目卡片显示当前阶段、失败数、待审核数和最近导出；
- 单项目备份与恢复。

MVP 仍然不增加：

- 无限画布；
- 通用节点式图片工作流；
- 三层 Agent 编排；
- 向量记忆；
- AI 视频生成轨道；
- 复杂分镜动画；
- Skill 商店；
- 任意 TypeScript 供应商代码在线执行。

### 22.13 最终判断

Toonflow 证明了“小说不是一次性输入，而是长期可查询的章节库；人物不是提示词片段，而是可复用资产；分镜不是孤立图片，而是与资产和剧本关联的生产记录”这一方向是正确的。

对北派说书项目，最合适的策略仍然不是整仓 fork Toonflow，也不是让新项目运行时依赖完整 Toonflow，而是做一个更窄的独立项目：允许选择性抽取和改造适合的后端代码、数据结构与提示词，同时补齐 Toonflow 没有覆盖的大 TXT 编码识别、字符偏移、原文哈希、可靠任务恢复、TTS、字幕和 `ffmpeg` 固定模板。无限画布、AI 视频轨道、多层 Agent 和通用节点系统不进入首版。

## 23. 当前已确认与尚未确认

### 已确认

- 参考视频主体形式是静图说书，不需要角色动画；
- 开头问题、连续剧情和结尾悬念是核心；
- MuseDock 已具备大量可复用底层能力；
- 《北派盗墓笔记》适合按故事弧拆分为长视频；
- 新项目应独立，但不应复制整个 MuseDock；
- 第一版应采用固定模板和分段恢复；
- 第一版视频渲染直接使用 `ffmpeg`，不使用 HyperFrames、Chrome/Playwright 或逐镜头 HTML；
- 借鉴并可选择性复用 Toonflow 的章节事件摘要、分层改编、主资产/状态资产、候选图历史和显式资产关系；不整仓 fork，也不依赖完整 Toonflow 运行时；
- 第一版采用固定步骤工作区，不引入无限画布、三层 Agent、向量记忆或 AI 视频生成轨道；
- 先做 3～5 分钟样片，再扩大时长。

### 尚未确认

- 新项目名称；
- 新项目仓库位置；
- 首条样片具体章节；
- 最终 TTS 供应商和声音；
- 生图供应商是否支持参考图；
- 单集目标成本；
- 单集最终目标时长；
- 是否加入 BGM；
- 是否保留第一人称；
- 发布和商业化授权范围；
- 新项目与 MuseDock 共享代码的物理方式：共享包、抽取模块或有限迁移。

## 24. 推荐下一步

下一步不要直接大规模编码。先做一个独立项目的实施规格，至少确定：

1. 新项目名称与目录；
2. 首条《北派盗墓笔记》样片原文范围；
3. 3～5 分钟目标成稿字数；
4. TTS 声音与语速；
5. 唯一的第一版视觉模板；
6. 需要从 MuseDock 抽取的最小模块清单；
7. 借鉴 Toonflow 后确定的书库、分集、章节事件、资产、候选图、视觉段、任务和渲染分片数据结构；
8. 提示词版本、人工审稿和资产审核闸门；
9. 单项目备份与恢复格式；
10. MVP 验收标准；
11. 版权使用边界。

随后按以下顺序落地：

```text
新项目骨架
-> TXT 导入与章节索引
-> 章节事件摘要
-> 选择原文与忠实改编
-> 人工审稿闸门
-> TTS 与字幕
-> 主资产与阶段状态资产
-> 视觉段绑定与批量生图
-> 图片联系表与人工审核
-> 固定模板
-> 分段渲染和恢复
-> 首条样片
-> 实际发布数据验证
```

这份文档作为当前对话的项目基线。后续如果开始实施，应另外编写新项目的设计规格和分阶段任务计划，不在本文件中继续堆积实现细节。
